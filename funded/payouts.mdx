Ordinary profit is a two-way split. Vault and protocol take none of it.

```
builderShare = floor(profit × builderPoolBps / 10_000)
traderShare  = profit − builderShare
```

`builderPoolBps` is pinned at activation, 10%-70%. 20/80 is a common product term, not a protocol constant.

On self-funded both buckets hit the same address. The trader gets 100%.

Protocol and LPs earn from premium, subscription and forfeited surplus. Not from a keep-profit withdrawal.

## Withdraw profit

Profit is `currentEquity − A`. Not high-water mark.

All of this must hold:

- Active, term still live
- no pending trader-close intent
- TARGET not reached
- profit at least $1
- account flat
- enough tradeable Core USDC

Then either:

- **3** profitable checkpoint days (equity grew at least **0.70%** vs the previous checkpoint), or
- profit **≥ 3% of `A`**

The request snapshots the whole profit and bridges Core → EVM. `claimWithdrawal` then pays the split: trader residual from the clone, builder share to the pull ledger.

After a proven claim, peaks reset to `A`. A rejected Core send can be cancelled. Stored peaks do not weaken.

On a one-day self-funded term the first checkpoint is at expiry. In-term withdrawal is the 3% path only.

## Close

One reason, written once. Floors decide when. They are not a fee. Settlement uses snapshotted `Q` only.

| Reason | Unwithdrawn `max(Q − A, 0)` |
|---|---|
| Drawdown | Forfeited |
| TraderRequested | Forfeited |
| TARGET | Ordinary split |
| Subscription expired | Ordinary split |
| Subscription cancelled (sponsored) | Ordinary split |
| Admin | Ordinary split |

Profit already in a pending withdrawal stays vested. It is never mixed into `Q`. Even on a forfeiting close that piece still splits by `builderPoolBps`.

### Forfeited surplus

```
builder    = 40% of (Q − A)
protocol   = 20%
vault / LP = residual
trader     = 0
```

Unused `R` returns to `reserveRecipient`. Direct sponsor: the builder. Self-funded: the trader. Only actual principal loss consumes reserve.

### Voluntary close

A flat owner can request close. That is intent, not the reason. After the proxy drains positions and orders, the relayer commits `TraderRequested`. Withdraw and claim first if you still can.

## Settlement

```
principalLoss   = max(A − Q, 0)
reserveConsumed = min(R, principalLoss)
reserveRefund   = R − reserveConsumed
closeProfit     = max(Q − A, 0)
```

Settlement credits fixed recipients. It does not push USDC.

Anyone can call `claimPayout(recipient)`. Funds go only to that address. Several accounts can aggregate on one recipient.

Vault share of premium, subscription and forfeited surplus stays in NAV. It does not enter the ledger.

<Warning>
A forfeiting close zeros unwithdrawn close profit. Withdraw and claim first if the account is still eligible.
</Warning>
